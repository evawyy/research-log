### 进展 2：PDHCG CUDA 兼容性修复

- **行动：** 针对新版 CUDA / cuSPARSE API 变化，为 PDHCG 增加基于 `CUSPARSE_VERSION` 的兼容判断。
- **结果：** CUDA 13.3 / cuSPARSE 12.8.2+ 使用新的 `cusparseSpMVOp_bufferSize` 和 `cusparseSpMVOp_createDescr`，并显式传入 `CUSPARSE_SPMVOP_ALG_DEFAULT`；CUDA 13.2 / cuSPARSE 12.7.x 保留旧版 SpMVOp API；更旧版本 fallback 到标准 `cusparseSpMV` 路径。
- **证据/文件：** 已分别运行 `cmake --build build-cuda133 --parallel 4` 和 `cmake --build build-cuda132 --parallel 4`。
- **判断：** 兼容性修改没有破坏 CUDA 13.2，同时解决了 CUDA 13.3 下的构建问题，适合整理成 PR。

## 实验记录（没有可删除）

- **问题/假设：** 对同一个 convex QCQP，比较直接使用自己的 QCQP solver、转化为 SOCP 后使用 HRQ、使用 PDHCG 三条路线的速度、稳定性和收敛表现。
- **设置：** 已跑通 HRQ 和 PDHCG 两个 baseline；开始整理 HAMS 榜单中的测试实例，并寻找适合的 convex QCQP benchmark。
- **结果：** QCQP 统一 benchmark 尚未完成，但实验环境和 baseline 已经进入可推进状态。
- **结论：** 下一步应优先拿到可复现测试集，统一 stopping criterion、tolerance、time limit、硬件和线程设置。
- **是否需要复现：** 需要。后续每个 solver 都要记录环境、命令、数据、输出、失败原因和统一评测口径。

## 阅读记录（没有可删除）

- **材料与范围：** QCQP / functional SOCP / standard SOCP 之间的关系；KKT 条件；centered gap、error bound、quadratic growth；Exact-x / APDB 步长和 backtracking；Nesterov acceleration；saddle point formulation；GRIMIP 日志与流程。
- **我已经理解：** 不同 formulation 与 KKT 条件之间需要先建立对应关系，才能做公平 solver 对比；GRIMIP 的调参收益需要在长实例和独立重测中观察。
- **仍不理解：** convex QCQP benchmark 的最佳来源；HAMS 中哪些实例可直接使用；QCQP 转 SOCP 的统一转换细节；GRIMIP 中多线程、异常参数和 LLM response time 对结果的影响边界。
- **与当前研究的关系：** 这些问题直接决定后续 QCQP solver 对比实验是否公平，以及自动调参实验结论是否可信。
